# Commit: test: cover CLI honest failure for unrelated query

## Что было целью шага

Целью этого шага было добавить точечную regression-проверку на уровне CLI для сценария, где пользователь задаёт вопрос, не связанный с проиндексированными документами. Проект уже умел честно отказывать при недостаточном контексте, но на уровне CLI это поведение было зафиксировано только для пустого запроса, а не для обычного нерелевантного вопроса.

## Почему это следующий правильный маленький шаг

Это маленький и безопасный шаг, потому что он не расширяет архитектуру и не меняет пользовательский интерфейс. Мы просто уточняем уже существующий контракт честного отказа в том месте, где пользователь реально работает с системой: в команде `ask`. Такой тест помогает не потерять grounded-поведение при будущих изменениях retrieval и answer flow.

## Как работает новый код

Тест `test_run_cli_hides_sources_for_unrelated_query()` в [backend/tests/test_cli.py](/home/artur/project/grounded-rag-assistant/backend/tests/test_cli.py) выполняет полный маленький CLI-сценарий:

1. создаёт временную директорию;
2. записывает туда файл `alpha.txt` с коротким текстом;
3. вызывает `run_cli(["index", ...])`, чтобы построить локальный JSON-индекс тем же путём, которым пользуется настоящий CLI;
4. вызывает `run_cli(["ask", ...])` с запросом `"cat"`;
5. проверяет, что:
   - CLI завершился с кодом `0`;
   - в выводе есть строка `Answer: I could not answer from the retrieved context...`;
   - блока `Sources:` в выводе нет.

Это важно: тест не вызывает низкоуровневые функции retrieval и answering напрямую, а проходит именно через `run_cli()`. Значит, он проверяет не только бизнес-логику, но и пользовательский рендеринг результата в терминале.

## Почему решение сделано именно так

Выбран именно нерелевантный короткий запрос `"cat"`, а не длинная естественная фраза, потому что текущий `FakeEmbeddingProvider` в проекте строит очень простые детерминированные векторы на основе символов. Для этого шага было важно зафиксировать честный отказ без расширения области работ до переработки embedding-логики. Короткий нерелевантный запрос даёт стабильный и детерминированный regression-сценарий в текущей архитектуре.

## Что было до изменения

До этого изменения в CLI был только тест `test_run_cli_hides_sources_when_context_is_insufficient()`, который проверял поведение для пустого запроса. Это полезный edge case, но он не моделирует обычный пользовательский сценарий, когда вопрос сформулирован нормально, но не связан с содержимым индекса.

## Что стало после изменения

После изменения в проекте есть явная regression-проверка того, что CLI:

- умеет индексировать документы локально внутри теста;
- умеет честно отказать на нерелевантный запрос;
- не печатает `Sources:` в недостаточном контексте.

То есть контракт "лучше честно не ответить, чем придумать" теперь зафиксирован на CLI-уровне более реалистично.

## Как это влияет на общую архитектуру

Архитектура проекта не изменилась. Этот шаг усиливает слой проверки качества вокруг уже существующего пайплайна:

`index -> save index -> load index -> retrieval -> answering -> CLI rendering`

Тест полезен именно как связующее звено между retrieval/answering и пользовательским интерфейсом CLI. Он подтверждает, что grounded-поведение сохраняется не только внутри отдельных модулей, но и в конечном пользовательском сценарии.

## Ограничения текущего решения

Текущий regression-сценарий всё ещё завязан на `FakeEmbeddingProvider`, а он специально упрощён для детерминированных тестов. Поэтому тест фиксирует надёжный пример нерелевантного запроса в рамках текущей embedding-модели, но не является полноценной semantic-evaluation проверкой.
