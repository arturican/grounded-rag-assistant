# CLI regression for page-aware source rendering

## Цель шага

Добавить один узкий regression-тест на уровне CLI, который проверяет user-facing формат источников для чанка с метаданными страницы. Этот шаг нужен, чтобы зафиксировать поведение слоя вывода: если retrieval уже вернул источник с `page`, то пользователь в блоке `Sources:` должен увидеть человекочитаемый суффикс `page N`.

## Почему это следующий маленький шаг

До этого в проекте уже была проверка, что CLI:

- умеет индексировать и отвечать;
- показывает блок `Sources:` для релевантного ответа;
- скрывает `Sources:` для нерелевантного запроса.

Но не было отдельной regression-проверки именно на форматирование источника с номером страницы. Это маленький, локальный и логичный следующий шаг: не расширять архитектуру, не добавлять новые зависимости и не трогать прикладной код, а только зафиксировать уже существующее поведение через один явный тест.

## Что изменено

Изменения сделаны в четырёх местах:

- в `backend/tests/test_cli.py` добавлен новый тест `test_run_cli_renders_page_numbers_in_sources_block`;
- в `docs/NEXT_STEP.md` следующий шаг смещён на симметричную regression-проверку для непагинированного источника;
- в `docs/commit-notes/README.md` добавлена ссылка на эту заметку;
- создан этот markdown-файл с разбором шага.

При этом прикладной код CLI, answer layer и retrieval не менялся, потому что новый тест не обнаружил баг в текущем поведении.

## Как работает новый тест

Тест идёт самым узким и детерминированным путём:

1. Создаёт временную рабочую директорию и маленький локальный документ с текстом `Alpha facts live here.`
2. Вызывает существующий `index_directory(...)`, чтобы получить корректный сохранённый индекс с реальными embedding-данными и текущим форматом JSON.
3. После этого точечно правит уже сохранённый `index.json`:
   - меняет `source` на путь вида `paged.pdf`;
   - задаёт `page = 7`;
   - синхронно обновляет `chunk_id`, чтобы он явно отражал страницу.
4. Запускает настоящий CLI ask flow через `run_cli(["ask", ...])`.
5. Проверяет:
   - что команда завершилась с кодом `0`;
   - что в выводе есть блок `Sources:`;
   - что в выводе есть точная строка источника в текущем формате CLI: `- <path> page 7 (<chunk_id>)`.

То есть тест не проверяет форматирование косвенно и не ищет отдельные фрагменты по частям, а фиксирует полный user-facing рендер строки источника.

## Почему решение сделано именно так

У этого решения несколько причин:

- оно использует уже существующий CLI flow, а не изолированную проверку helper-функции, поэтому действительно защищает regression на пользовательском уровне;
- оно не требует настоящего PDF-парсинга и не добавляет внешние зависимости;
- оно не дублирует логику построения индекса вручную: сначала создаётся реальный индекс через текущий код, а потом минимально подменяются только поля метаданных, важные для этого сценария;
- оно остаётся стабильным и быстрым, потому что использует временные файлы и маленький fixture.

Именно поэтому шаг получился маленьким, безопасным и при этом полезным.

## Какие тесты запущены

Запущен узкий модульный набор, который и требовался для этого шага:

```bash
python3 -m unittest backend.tests.test_cli -v
```

## Результат проверки

Новый тест проходит вместе с уже существующими CLI-тестами. Это подтверждает, что текущий CLI-путь действительно отображает источник с номером страницы в формате `page N`, и регрессия на этом уровне теперь зафиксирована.

## Ограничения

- Проверка всё ещё опирается на искусственно подготовленный сохранённый индекс, а не на end-to-end PDF ingestion.
- Тест покрывает только один положительный сценарий с одной страницей и одним источником.
- Отдельно не проверяется симметричный случай для источника без `page`, когда суффикс `page N` не должен появляться.

Эти ограничения сознательные: задача была именно про минимальный следующий шаг на уровне CLI regression coverage.
