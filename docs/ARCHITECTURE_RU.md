# Архитектура проекта

Этот файл объясняет проект как цельную систему, а не как набор отдельных коммитов.

## Главная идея

Проект строит grounded RAG-пайплайн:

1. прочитать документы пользователя;
2. разбить текст на чанки;
3. превратить чанки в векторы;
4. найти самые релевантные чанки по вопросу;
5. собрать ответ только из найденного контекста;
6. вернуть источники, чтобы можно было проверить ответ.

Главный принцип проекта: лучше честно сказать "не знаю", чем придумать ответ без опоры на найденные данные.

## Как проходит запрос через систему

### Сценарий `index`

Когда пользователь индексирует документы, цепочка сейчас такая:

1. CLI или API вызывает индексирование директории.
2. Для каждого файла выбирается подходящий загрузчик.
3. Загруженный текст превращается в чанки.
4. Для чанков строятся эмбеддинги.
5. Чанки и их векторы сохраняются в локальный индекс.

### Сценарий `ask`

Когда пользователь задаёт вопрос, цепочка такая:

1. Загружается ранее сохранённый индекс.
2. Для текста запроса строится эмбеддинг.
3. Retrieval-слой ищет ближайшие чанки.
4. Answering-слой проверяет, достаточно ли хороший найден контекст.
5. Если контекст достаточный, ответ собирается из retrieved chunks.
6. Если контекст слабый, возвращается явный отказ без фантазии.

## Основные модули

### `backend/app/models.py`

Здесь лежат базовые структуры данных:

- `DocumentChunk` — обычный чанк документа;
- `RetrievedChunk` — чанк после retrieval с добавленным `score`.

Это фундамент пайплайна. Практически все остальные слои работают именно с этими моделями.

### `backend/app/chunking.py`

Этот модуль отвечает за подготовку текста к retrieval:

- нормализует пробелы;
- делит текст по абзацам;
- режет длинные абзацы на окна с overlap.

Смысл этого слоя в том, чтобы не индексировать огромные сырые документы целиком. Retrieval лучше работает по маленьким смысловым кускам.

### `backend/app/loaders.py`

Это слой чтения документов.

Сейчас он умеет:

- читать `.txt`;
- читать `.md`;
- работать через контракт для `.pdf`.

Здесь важно, что ingestion не должен знать детали форматов файлов. Он просто просит загрузить документ, а loaders уже решают, как это сделать.

### `backend/app/ingestion.py`

Этот модуль соединяет загрузку документа и chunking.

Его задача: взять загруженный документ и превратить его в список `DocumentChunk` с корректными:

- `chunk_id`;
- `source`;
- `page`;
- `chunk_index`;
- `text`.

Это мост между сырым файлом и retrieval-системой.

### `backend/app/embeddings.py`

Здесь находится интерфейс провайдера эмбеддингов.

Почему это важно:

- код retrieval не зависит от конкретной ML-библиотеки;
- тесты можно гонять на fake-провайдере;
- реальный embedding backend можно подключить позже без переписывания всего проекта.

Сейчас в проекте уже есть `FakeEmbeddingProvider`, который делает поведение тестируемым и детерминированным.

### `backend/app/retrieval.py`

Этот модуль хранит индексированные чанки и умеет искать релевантные результаты.

На текущем этапе это in-memory реализация:

- получает чанки;
- получает для них эмбеддинги;
- хранит их рядом с метаданными;
- по запросу возвращает `top_k` лучших результатов.

Именно здесь формируется ranked output, который потом потребляет answering-слой.

### `backend/app/answering.py`

Здесь зафиксировано главное правило grounded RAG:

- использовать только найденный контекст;
- прикладывать источники;
- честно отказывать при недостатке контекста.

На текущем этапе ответ детерминированный: функция не генерирует новый текст через LLM, а собирает ответ напрямую из найденных чанков. Это полезно для ранней стадии проекта, потому что поведение легко тестировать и понимать.

### `backend/app/index_store.py`

Этот модуль отвечает за сохранение и загрузку локального индекса. Он нужен, чтобы разделить два сценария:

- сначала один раз индексировать документы;
- потом много раз задавать вопросы к уже сохранённому индексу.

Без этого пришлось бы заново строить индекс на каждый вопрос.

### `backend/app/cli.py`

Это текущий основной пользовательский интерфейс проекта.

Команды:

- `index` — строит локальный индекс по директории документов;
- `ask` — отвечает на вопрос по сохранённому индексу.

CLI важен как первый вертикальный срез: через него можно проверить весь пайплайн целиком без UI и без браузера.

### `backend/app/api.py`

Это HTTP-обёртка над существующим пайплайном.

Эндпоинты:

- `/health`;
- `/index`;
- `/ask`.

API не должен дублировать бизнес-логику. Его задача — аккуратно переиспользовать уже существующие функции и отдать понятные request/response схемы.

Для локального demo API дополнительно разрешает CORS-запросы с фронтенд-origin:

- `http://127.0.0.1:5173`;
- `http://localhost:5173`.

### `frontend/`

Это минимальный demo-клиент на React + TypeScript + Vite с одной страницей.

Фронтенд не вводит новую бизнес-логику, а только вызывает уже существующие API endpoint:

- `GET /health`;
- `POST /index`;
- `POST /ask`.

На странице отображаются loading/success/error состояния и поля ответа:

- `answer`;
- `used_context`;
- `sources`.

## Как слои зависят друг от друга

Упрощённо зависимости выглядят так:

`loaders -> ingestion -> embeddings/retrieval -> answering -> cli/api -> frontend`

При этом:

- `models.py` используется почти везде;
- `index_store.py` помогает сохранить состояние между `index` и `ask`;
- тесты проверяют каждый слой отдельно и несколько маленьких сквозных сценариев.
- frontend слой использует те же контрактные поля API, поэтому может служить прозрачной демонстрацией текущего состояния backend.

## Почему архитектура сейчас именно такая

Проект специально развивается от простого к сложному:

- сначала детерминированные модели и функции;
- потом сквозной CLI;
- потом API;
- потом evaluation;
- и только позже более тяжёлые улучшения вроде richer retrieval или UI.

Это хороший учебный подход, потому что на каждом шаге можно понять, что именно изменилось, и проверить поведение без магии.

## Что пока упрощено

Сейчас важно понимать ограничения текущей версии:

- retrieval пока in-memory, а не production-grade vector DB;
- answering пока не использует полноценную LLM-генерацию;
- PDF-слой подготовлен архитектурно, но ещё не доведён до полноценных реальных сценариев;
- evaluation только начинает формироваться через маленькие regression-checks.

Это не недостаток для учебного этапа. Наоборот, так проще увидеть скелет системы без лишнего шума.
