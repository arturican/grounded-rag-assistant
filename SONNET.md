# SONNET.md

## Цель проекта

Собрать grounded RAG-систему, которая отвечает только по найденному контексту и всегда возвращает источники.

## Краткая карта архитектуры

- `backend/app/loaders.py` - чтение `.txt/.md/.pdf` в единый формат.
- `backend/app/ingestion.py` + `backend/app/chunking.py` - построение чанков с метаданными.
- `backend/app/embeddings.py` + `backend/app/retrieval.py` - векторизация и top-k retrieval.
- `backend/app/answering.py` - deterministic grounded answer + честный отказ.
- `backend/app/index_store.py` - сохранение/загрузка локального индекса.
- `backend/app/cli.py` и `backend/app/api.py` - пользовательские интерфейсы.
- `frontend/` - demo-клиент, не источник бизнес-логики.

## Как читать проект

1. `AGENTS.md`
2. `docs/PROJECT_BRIEF.md`
3. `docs/ROADMAP.md`
4. `docs/NEXT_STEP.md`
5. `docs/ARCHITECTURE_RU.md`
6. затем код (`backend/app`, `backend/tests`, `frontend`)

## Как выполнять шаги из stepes.md

В репозитории нет `stepes.md`/`STEPS.md`; роль текущего шага выполняет `docs/NEXT_STEP.md`.
Рабочий цикл:

1. прочитать шаг и ограничение scope;
2. доказать проблему (или подтвердить, что шаг уже закрыт);
3. сделать минимальный фикс;
4. добавить/обновить узкий тест;
5. прогнать только релевантные проверки;
6. обновить docs и `docs/NEXT_STEP.md` на следующий маленький шаг;
7. один шаг = один commit + одна note в `docs/commit-notes/`.

## Как искать ошибки

- Сверять контракт между `backend/app/api.py`, `frontend/src/types.ts`, `frontend/src/api.ts`.
- Проверять honest-failure path (`used_context=false`, пустые sources).
- Проверять сохранность метаданных `source/page/chunk_id` через ingestion -> retrieval -> answer -> render.
- Искать docs drift: README, architecture, NEXT_STEP должны описывать текущее поведение.

## Когда менять код, а когда сначала тест

- Сначала тест: если есть риск регрессии или поведение спорное.
- Сразу код + test-near: если ошибка очевидная и локальная (например, отсутствующая проверка входа).
- Нельзя закрывать шаг без теста на измененное поведение.

## Как оформлять commits

- Один commit решает одну задачу.
- Сообщение: кратко "почему", а не список механических действий.
- Не смешивать bugfix, рефакторинг и docs в одном шаге без необходимости.

## Как оформлять commit notes

Формат note:

- цель шага;
- почему это следующий правильный шаг;
- что найдено;
- что изменено;
- как работает новое поведение;
- затронутые файлы;
- какие тесты запущены и результат;
- ограничения;
- следующий маленький шаг.

## Что нельзя делать

- массовые рефакторинги вне текущего шага;
- изменение API-контрактов без необходимости;
- добавление зависимостей без прямой причины;
- заявление "исправлено", если тесты/проверки не запускались;
- оставлять `docs/NEXT_STEP.md` и README в устаревшем состоянии.
